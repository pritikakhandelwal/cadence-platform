# cadence-db

Shared SQLAlchemy models — `User`, `LoginSecurity`, `UserSession`, `Analysis` — used by both `apps/api` and `apps/worker`. Both processes read `DATABASE_URL` and talk to the same Postgres (or SQLite, the default/test fallback) directly; there's no callback API between them. This is what lets `apps/worker`'s `detect_tracks_job` write a finished `AnalysisResult` straight into the row `apps/api`'s `GET /analyses/{id}` reads back.

Moved out of `apps/api` (where it started in Phase 1) once `apps/worker` needed to write to the same rows in Phase 2 — see [`../../docs/decisions.md`](../../docs/decisions.md) and [`../../STATUS.md`](../../STATUS.md) for why shared-DB was chosen over a callback API.

## Install

```bash
pip install -e .
```

(Already listed as `-e ../../packages/db` in `apps/api/requirements.txt` and `apps/worker/requirements.txt`.)

## Migrations

Alembic, with the migrations shipped inside the package (`cadence_db/migrations/`) and an `alembic.ini` here for the CLI. It reads `DATABASE_URL` like the apps do:

```bash
cd packages/db
alembic upgrade head                                   # bring a database to the current schema
alembic revision --autogenerate -m "what changed"      # after changing a model -- then read it
alembic upgrade head --sql                             # print the SQL instead of running it
```

**Two sources of truth, one guard.** `init_db()` (`Base.metadata.create_all`) is still what dev and the tests use; Alembic is for any database that has to keep its data across a schema change. `apps/api/tests/test_migrations.py` fails if the two disagree -- change a model without generating a migration and it goes red (checked by mutation, including on Postgres for a naive-vs-timezone-aware column). Don't mix them on one database: a database built with `create_all` has no `alembic_version` table.

The baseline (`0001`) was autogenerated against an empty PostgreSQL 16 and reviewed. A database created with `create_all` *before* the timezone fix has naive `TIMESTAMP` columns and needs converting before it's stamped -- see the docstring in `versions/0001_initial_schema.py`. None is known to exist.

What's not covered: no data migrations have been written or tested (there's only the baseline, so nothing to migrate yet), and nothing runs `alembic upgrade head` automatically on deploy.

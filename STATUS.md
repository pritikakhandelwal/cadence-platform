## Phase 2 — Lock-on — **built, fast, and wired end-to-end for the auto-lock path**

`apps/worker/worker/pipeline/` (see that app's README for the module breakdown):

- [x] YOLO person detection + ByteTrack/BoT-SORT tracking (`detection.py`, via `ultralytics .track()`)
- [x] Pose-on-crop-only via RTMPose (`pose.py`, via `rtmlib`) — never runs on the full frame, so a second person or a mirror can't corrupt the signal
- [x] Short-gap (≤3 frames) linear interpolation, longer gaps left as real discontinuities (`interpolation.py`)
- [x] One-Euro jitter smoothing, per joint/axis (`smoothing.py`)
- [x] Track summaries for a future multi-person "pick your dancer" UI, and a quality gate (reliable-frame %, fragmentation, person count) that rejects a bad lock with a human reason (`quality.py`)
- [x] 20 fast unit tests (no ML deps needed) covering smoothing/interpolation/quality-gate logic in isolation — passing
- [x] 2 integration tests that run the **real** pipeline against a real solo dance clip (`professional_dance.mp4`, not committed — see `apps/worker/README.md`) — both passing: detection finds the dancer, tracking holds them through the clip, pose comes back with plausible non-zero keypoints, the quality gate passes
- [x] **Performance problem found and fixed.** First version took ~48 minutes for a few seconds of video on CPU, because `pose.py` used `rtmlib`'s `Body`, which runs its *own* internal YOLOX person detector on every cropped frame — on top of the YOLO detection already done for tracking. Fix: read `Body`'s source (`rtmlib/tools/solution/body.py`) to find which onnx checkpoint + input size it resolves for a given `mode`, then call `rtmlib.RTMPose` directly with that checkpoint and our own bbox — `RTMPose.__call__(image, bboxes=[bbox])` takes the *full* frame and does its own internal affine crop per bbox, so "pose on crop only" still holds with one model per frame instead of two. Re-measured on the same real clip (432 frames): pose estimation is now ~33ms/frame (~14s for the whole clip), and the full integration suite (detect + lock + pose) runs in **76 seconds**, down from 48 minutes — about a 38x speedup on the full suite, more on pose alone. Both integration tests still pass with correct-looking output (COCO-17 keypoints, confidence scores 0.9+ on a clean solo clip).
- [ ] No eval dataset yet (roadmap's "film 30 clips yourself" for MOTA/IDF1, reliable-frame %, false-lock-on-mirror numbers) — this is still nowhere near that. Two synthetic clips were spot-checked (built with `ffmpeg` from the same real solo footage, not real duo/mirror recordings) with real, mixed results:
  - **Duo (two different real dancers, side by side):** handled correctly. 2 distinct tracks, each 100% frame coverage, 1 fragment, no ID confusion. Locking onto either one gives a clean quality-gate pass, and `person_count=2` correctly reflects the other dancer without penalizing the locked track's own reliability.
  - **Mirror (one dancer + their own horizontally-flipped reflection, side by side):** exposed a real gap, not a pass. YOLO+ByteTrack produced **4** track IDs for what's really one dancer + one reflection — heavy fragmentation on two of them (4 and 2 fragments), one spurious track at 2% frame coverage and 0.33 confidence. The quality gate still *passed* the top track (94% reliable, only 2 fragments) because our current thresholds are conservative enough to tolerate this — but nothing in the pipeline actually recognizes "this looks like a mirror," it just silently picked whichever track had the most frames. That is exactly the roadmap's "false lock on mirror" risk (target: 0), and this spot-check does not clear that bar. Not fixing this yet — a real fix (e.g. detecting near-mirrored bbox trajectories, or geometric symmetry checks) needs more than one synthetic clip to validate against; recorded here as a known, real limitation rather than papered over.
- [x] **`apps/api` now actually enqueues this.** Decided the open "shared DB vs. callback" question from the previous entry: `apps/worker` and `apps/api` both talk to the same Postgres/SQLite directly via a new shared [`packages/db`](packages/db) package (matches the roadmap's own architecture diagram, where both connect to PostgreSQL). `POST /analyses` enqueues `detect_tracks_job(analysis_id, video_path)` via a real arq pool (`apps/api/app/queue.py`, overridable in tests — no live Redis exists in this dev environment to test against for real, same caveat as Postgres above). The job runs detection, then either auto-locks a single confident track and writes a final `complete`/`rejected` `AnalysisResult` into the same row `GET /analyses/{id}` reads, or (see next bullet) marks it `needs_dancer_pick`.
- [x] **New: `is_lock_ambiguous` heuristic** (`worker/pipeline/quality.py`) refuses to auto-lock when no track is clearly dominant, instead of always grabbing whichever track has the most frames. Directly motivated by the mirror stress-test finding below — with this wired into `detect_tracks_job`, both the duo clip and the mirror clip now correctly come back `needs_dancer_pick` instead of the mirror case silently completing on a guess. Only validated against these same two synthetic clips, not a real eval set — treat the 0.5 dominance-ratio threshold as a reasonable default, not a tuned one.
- [x] Verified for real: a new integration test (`test_tasks_integration.py`) creates a real `Analysis` row, calls `detect_tracks_job` against the real solo clip, and confirms the row ends up `complete` with a valid `AnalysisResult` and `reliable_frame_pct > 50` — not just that the pipeline functions return sensible values in isolation, but that the actual job-writes-to-DB path works. (Caught and fixed a real bug while building this: the test's `DATABASE_URL` override was applied *after* `cadence_db` had already been imported via `pytest.importorskip`, so it silently wrote to a stray `apps/worker/cadence.db` instead of the intended temp file. Reordered so the env var is set before any import of `cadence_db`; re-ran to confirm no stray file appears anymore.)
- [x] **`needs_dancer_pick` now has an API to resolve it.** `GET /analyses/{id}/candidate-tracks` lists the ambiguous tracks (track_id, frame_count, mean_confidence, fragments — pulled from what `detect_tracks_job` already stashed in `Analysis.pending_lock_data`), and `POST /analyses/{id}/lock` (body `{"track_id": int}`) enqueues `extract_locked_pose_job`, which resumes from the stashed detections (no re-running YOLO), writes the final `complete`/`rejected` result into the same row, and clears `pending_lock_data`. Verified for real: a new integration test seeds an analysis in `needs_dancer_pick` state with real detections from the solo clip, calls `extract_locked_pose_job` directly, and confirms it ends up `complete`. Endpoint-level behavior (candidate-tracks listing, rejecting an unknown track_id, rejecting a non-pending analysis, enqueue happening with the right args) covered by 6 new `apps/api` tests using a seeded DB row, since producing `needs_dancer_pick` organically needs a real duo/mirror upload through a live worker, which this dev environment can't run end-to-end (no Redis).
- [x] **`POST /analyses` now also accepts a YouTube link for the reference video** (`professional_video_url`, alternative to uploading `professional_video` — exactly one required). Downloaded via `yt-dlp`, restricted to `youtube.com`/`youtu.be` hosts over `http`/`https` only (never an arbitrary URL — that's a real SSRF surface on a server), then run through the same `ffprobe` validation an upload gets. ## Phase 3 — Coaching intelligence — **built and wired end-to-end; one real limitation found and documented, not hidden**

Legacy's `modules/dtw_compare.py` did raw, unnormalized per-frame DTW distance — no normalization, no joint angles, no confidence, no segment feedback, exactly the "fake score" Section 7 of the roadmap calls out. Replaced:

- [x] Joint-angle features (`apps/worker/worker/pipeline/features.py`) — 8 angles (elbow/knee/hip/shoulder, both sides) from RTMPose's 17 keypoints, automatically invariant to translation/scale/in-plane-rotation (no explicit Procrustes step needed for the angles themselves), plus a per-video baseline-corrected spine lean.
- [x] Confidence masking — a joint gets excluded (NaN), not silently trusted, if any of its 3 keypoints is below 0.3 confidence. Added *after* finding real large hip-angle "errors" in real footage that turned out to be low-confidence RTMPose guesses, not real signal — see below for the fuller, honest story on this.
- [x] DTW alignment on the feature sequences (`alignment.py`) — plain O(N\*M) numpy, no external dependency. Not verified to scale to the platform's 5-minute upload cap (an NxM table at 9000 frames would be ~650MB); fine for what's been tested (a few hundred frames).
- [x] Segmentation, joint-level residuals, and issue messages (`scoring.py`) — ~2s windows, `angle` issues over a 15-degree mean error, a `timing` issue for growing reference/user lag, and `score = 100 * exp(-mean_error/TAU)` (TAU set so 20 degrees average error = 50%) — a formula over a normalized, aligned feature, not raw pixel distance. See `docs/decisions.md` for why that distinction is the actual fix, not "score = 100 - d\*2 but sneakier."
- [x] **Four more issue types added: `occlusion`, `tempo`, `energy`, `balance`** (plus un-suppressing torso lean as a real `angle` issue, and a new `balance_offset` feature for it to use). Driven by a claude.ai/design questionnaire that asked which issue categories the product should surface — rather than answer the checklist without building the backing logic, built real detection for all of them: `occlusion` (a joint too low-confidence to trust for >=30% of a window — captured from the NaN mask *before* DTW's imputation fills it in, so it reflects genuinely missing data, not a post-hoc guess), `tempo` (DTW path locally stretched/compressed past a 0.6x-1.6x ratio, a proxy for a skipped/rushed or added/repeated move), `energy` (limb movement under half the reference's, only checked when the reference itself has enough motion to compare against — guards against flagging "low energy" when the reference itself is nearly still), and `balance` (hip position wandering from the ankle-to-ankle base of support more than the reference's own baseline, via the new `balance_offset` feature in `features.py`). Arm-vs-leg and footwork-vs-arm-position distinctions needed no new issue type at all — the existing `angle` issue's `joint` field (e.g. `left_elbow` vs `left_knee`) already carries that distinction; a separate type would have been a redundant schema field for information already present. `IssueType` extended in both `packages/schema/python` and `packages/schema/typescript` in lockstep (schema tests + TS typecheck both clean). 6 new unit tests added on top of the existing 53 (`apps/worker/tests/test_scoring.py`), all against synthetic ground-truth fixtures (independent smoothed random walks per joint, the same fixture design that worked for the original synthetic eval) — full worker suite: 59 passed, 3 skipped. Their thresholds are still first-pass defaults, not tuned against any real eval set.
- [x] **Real-footage verification caught a real regression before it shipped.** Running the existing real-motion planted-error regression test (`test_scoring_real_motion_eval.py`) against the rewritten `scoring.py` — not just the 59 synthetic unit tests, all of which stayed green throughout — found the new `occlusion` issue type had been placed *ahead* of `angle` issues in each window's issue list. On real footage, some joint dips below the confidence threshold for part of a window fairly often for reasons unrelated to whatever's actually wrong, so "the top issue" was frequently an irrelevant occlusion notice instead of the real angle error: attribution hit rate collapsed from the previously-measured 82% to 20% (well under the roadmap's 70% bar). Fixed by reordering so angle issues (specific joint, specific error — the real technique feedback) lead the list, with occlusion/balance/tempo/energy/timing as secondary context after. Re-ran: 80% (16/20), back above bar. Kept here, not just in a commit message, because it's a concrete instance of why this project runs a real-footage integration pass before calling something done — a synthetic-only check would have shipped this.
- [x] **The first run of the four new issue types on real footage found three more real bugs, none visible to any synthetic test** -- run through the real API -> queue -> worker -> DB path on the two real clips (~60 fps reference vs. ~30 fps user). (1) `tempo` fired in every window at ~0.5 because it compared raw frame counts, so a frame-rate difference read as "half the frames" -- now compares seconds. (2) Fixing that exposed `energy` firing in 3 windows at 0.39-0.47; a first fix (scale per-frame change by fps) was wrong and failed its own frame-rate-swap test, and even the corrected fixed-0.1s-lag version kept firing until an independent check -- whole-clip motion straight from the saved keypoints, identical for both dancers (16.85 vs. 16.96 deg) -- showed the flags were an artifact of reading DTW-path indices, where each 30 fps user frame repeats ~2x against a 60 fps reference. (3) `balance` fired twice at 0.62-0.70 hip-widths on ankle keypoints that clear the confidence bar in only 32-62% of frames (these clips cut off the legs) -- now gated on ankle visibility, the same rule `occlusion` uses. After the fixes the real pair yields `angle` 17 / `occlusion` 9 / `timing` 2 and no tempo/energy/balance; score unchanged at 38.65. **Caveat that matters:** this shows those three types stopped false-firing on one real pair, with a regression test per fix -- it does not show they fire correctly on real errors. True-positive evidence is still only synthetic, and the thresholds are still untuned defaults. Full write-up in `apps/worker/README.md`.
- [x] **True-positive evidence for `tempo`/`energy`/`occlusion` on real motion** (`apps/worker/scripts/eval_planted_signals.py`; fast subset in `tests/test_scoring_real_motion_eval.py`; `scripts/extract_keypoints.py` makes the input): planting one known change into a real pose sequence, both clips as bases, user at same and half fps -- `tempo` 30/36 (83%) with 0/32 false-positive windows, `energy` 10/10, `occlusion` 4/4. Reported honestly: the first run showed `energy` 4/8 and `occlusion` 2/4, and both were mistakes in the eval (wrong energy ground truth; a mask that left no whole window inside it), not the detector -- corrected once, code and thresholds untouched, numbers preserved in the README. Limits: the "user" is the reference with one edit (easier than two independent takes), 1.2 s skips are missed when they likely straddle a window boundary, and **`balance` still has no true-positive evidence** (needs a full-body clip -- ankles are too low-confidence on the available ones, so the gate correctly silences it).
- [x] `detect_tracks_job`/`extract_locked_pose_job` now run the reference video through the same detect+lock pipeline once the user's lock succeeds, save both keypoint sequences to the workspace (`*_keypoints.npz` — Phase 2 computed these and threw them away; that gap is now closed), and write a real `overall` score + `segments` into the `AnalysisResult`. `apps/api` needed zero changes to expose this — `GET /analyses/{id}` already returns whatever's in `analysis.result` generically, which is the payoff of freezing the schema in Phase 0.
- [x] **Synthetic planted-error eval, matching the roadmap's own bar** ("bad must score lower AND the top issue must match the planted error >= 70% of the time"). Took three fixture redesigns to get right — not because the scoring code was wrong, but because the *test's* synthetic motion could be gamed by DTW re-timing: a single animated joint let a constant offset get erased by matching a different phase of the same periodic wave; three independently-animated sine waves still left partial retiming freedom; linear ramps were the worst choice (a constant value-offset and a constant time-shift are mathematically interchangeable for a straight ramp). Independent smoothed random walks per joint finally worked — uncorrelated noise has no shift that mimics a constant offset. Full story in `apps/worker/tests/test_scoring.py`'s module docstring. With that fixture, a planted 25-degree elbow error is correctly attributed to `left_elbow` as the top issue in every synthetic segment.
- [x] **Real footage, checked against the actual video, not just trusted as a number.** Ran the two real solo clips (`professional_dance.mp4`, `user_dance.mp4`) through the complete real pipeline. Result: overall score ~39/100, `reliable_frame_pct=100%`, large (40-90 degree) hip-angle differences across all 3 segments. Before accepting that, extracted a real frame from each clip at a comparable timestamp and looked at them — the two dancers' arm positions are visibly different at that point, so a low score isn't obviously wrong. Then checked whether the hip-angle disagreement specifically was a confidence-masking artifact (hypothesis: TikTok-style vertical clips are often framed to cut off the legs) — it wasn't cleanly that: actual RTMPose confidence for those hip keypoints was ~0.6, moderate, not clearly garbage. Adding the confidence-masking fix above did measurably change the result (score moved 31 -> 39, one segment's `confidence` dropped to 0.78 reflecting some masking), but didn't make the hip disagreement disappear. Concluded (documented in `docs/decisions.md`, not fixed): this pipeline is 2D-only, so it cannot distinguish a genuine hip-angle difference from a camera-viewpoint difference between two independently-filmed clips. Real, unresolved limitation, not patched by tuning a threshold to make one example look nicer — there's no eval set yet to tune against legitimately.
- [x] **Real-motion planted-error eval** (`apps/worker/scripts/eval_planted_errors.py`, regression-tested in `tests/test_scoring_real_motion_eval.py`). Only one real clip pair exists on this dev machine and no real labeled good/bad pairs exist (that needs new footage), so this corrupts a REAL extracted pose sequence -- not the synthetic skeleton above -- with a KNOWN, controlled offset on one joint at a time, preserving real human motion's joint-to-joint correlation. Result: **82% single-joint attribution hit rate** on real motion, above the roadmap's 70% target, plus a genuine, non-obvious finding: hip/shoulder corruptions partially "leak" into the adjacent knee/elbow reading (2/4 instead of 4/4), because the corruption method moves a joint's distal keypoint, which is also the *vertex* of the next joint down the chain -- a limitation of this eval technique for adjacent-joint pairs, not a scoring bug. Elbow/knee corruptions (not sharing a keypoint with each other) hit 4/4 cleanly.
- [ ] No `path`-type issues yet (schema supports the enum value; nothing generates one).
- [ ] Still no eval dataset with independently *filmed* good/known-bad pairs — the roadmap's "10 phrase pairs, film 30 clips yourself" needs new footage this project doesn't have. What exists now: a synthetic ground-truth proxy (fully fabricated skeleton), a real-motion ground-truth proxy (real skeleton, fabricated error), and one real-but-unlabeled clip pair. Three different, complementary things -- none of them is the real eval battery the roadmap asks for.
- [ ] Alembic migrations still pending (same item as Phase 1, unchanged).

**What's real here:** the full pipeline runs against real footage end-to-end and writes a real, inspectable `overall` score and timestamped `segments` with joint-level issues into the database, the scoring logic has been checked against both a fully-synthetic and a real-motion ground truth that both meet the roadmap's 70% accuracy bar, and a real, non-obvious limitation of the real-motion eval method itself (adjacent-joint leakage) was found and explained rather than glossed over. **What's not real yet:** there is no eval set with independently filmed, hand-labeled clips, the 2D-viewpoint limitation is confirmed but unresolved, and — as with every phase so far — nobody outside a test can trigger any of this, because `apps/web` still calls nothing.
